# Kotlin codec timezone provider contract — Refs #121

Implementation contract for the portable provider, point resolver and three
calendar codecs. Main and system-account code are outside this migration. The ThreeTen provider has a confirmed semantic
defect: Asia/Gaza 2074 is accepted at 10:30Z instead of 09:30Z in the production
import/export path. Gregorian arithmetic in ThreeTen is a separate concern from
its timezone rules. A successful build or same-provider roundtrip cannot validate
those rules.

## Normative input and ownership

The shared generator, JSON, resolver.js, provenance, independent oracle and schema
remain the common normative source. Pinned input:
`port-adapters/timezones/tzdb-2026egtz.json`, schema 2, 597 identifiers/439 models,
SHA-256 `2e6b1c9da8c9b2a98d8b9c9c6addb4b93b6de37a19e76120361eff245cc87e9c`.
It has zero differences in 269,817 independent pinned zic/ZoneInfo checks. This
contract uses the normative ledger accompanying the shared payload; legacy BP
diagnostics are not runtime provenance.

Each identifier maps to one model index. A model is:
`[initialTypeIndex, types, historyPairs, tail]`. Types preserve integer offset
seconds, DST bit, abbreviation, standard/wall and UTC/local flags. History pairs
are UTC epoch seconds and the post-transition type index. The tail preserves
standard/DST offsets and names, original POSIX text, and M/J/N wall-clock rules
with signed times up to 167:59:59. Tail rules apply strictly after the final
historical transition; fixed tails must agree with the final active offset.

The Kotlin provider, codec adapters and VTIMEZONE generator consume this common
source without changing its models. The independent oracle remains separate from
Kotlin rule evaluation. No global BP registration, patched JAR, Main/bridge
changes or edits to canonical shared product source are part of this migration.

## Small provider contract

Logical immutable Kotlin contract (implemented by portable classes; epoch
**seconds**, unlike JS milliseconds):

```kotlin
interface ProviderZone {
    val identifier: String                 // requested alias, preserved on export
    fun offsetAt(epochSeconds: Long): Int  // seconds, never rounded minutes
    fun project(epochSeconds: Long): LocalDateTime
    fun validInstants(wall: LocalDateTime): List<Long> // sorted unique epochs
}
interface ProviderZoneDatabase {
    val version: String
    val payloadSHA256: String
    fun zone(identifier: String): ProviderZone // unknown/unsupported throws
}
enum class GapPolicy { REJECT, FORWARD, OMIT }
enum class FoldPolicy { EARLIER, LATER, REJECT }
// PointResolver resolves ProviderZone.validInstants and explicit gap transitions.
// Codecs always use REJECT/EARLIER; no global policy or OS-provider fallback.
```

Gregorian dates/times use BP LocalDate/LocalDateTime solely as value/arithmetic
objects. Projection adds the integer provider offset to epoch seconds, then uses
UTC-coordinate Gregorian conversion. This avoids BP ZoneOffset's +/-18h limit;
TZif has wider historical offsets. Arithmetic uses explicitly range-checked Long values and
validates final civil years 1..9999. No numeric standard offset is inferred from
DST samples. No `java.util.TimeZone.getOffset` or platform rules are consulted.
System configuration contributes only its identifier, once at the operation
boundary. Unsupported OS fixed-offset IDs must fail clearly at first; accepting
additional numeric-ID spellings requires a reviewed shared policy, not a fallback
that invents named-zone rules.

Parsing validates schema/version/hash, array sizes/indexes, ordered history,
bounds/flags, alias names, original POSIX text against parsed tail, and history/
tail continuity. Validated data is immutable and cached once. Same model aliases
share data but retain the requested identifier. `Factory` remains explicitly
unsupported. UTC/GMT/UT/Z aliases follow the shared resolver exactly; no casefold
or guessed/canonicalized fallback.

## Calendar semantics retained

1. DATE is a date, independent of timezone/DST. Existing UTC-coordinate sentinel
   math and exclusive all-day end rules remain; no midnight zone lookup is added.
2. UTC `Z`/DATE use a typed null source, never a freely choosable string sentinel.
   Otherwise calendar-scoped embedded VTIMEZONE wins even if
   its TZID equals a known named zone or alias. Floating values resolve in the
   operation's display zone; a named source without an embedded block uses the
   normative provider. Unknown names never become UTC or the system zone.
3. EmbeddedZone remains its existing bounded resolver, including second offsets
   up to RFC 5545's +/-23:59:59. Export's existing source-definition probe through
   the importer can remain for this narrow migration; extracting that mechanism
   is not necessary to remove BP named-zone rules.
4. Gaps reject and folds choose the earliest valid instant as currently specified
   by these codecs. The generic point layer may expose forward/omit/later/reject
   for cross-provider parity tests; callers do not silently change policy.
5. Durations add W/D as Gregorian source-wall days, resolve that wall point, then
   add H/M/S as elapsed seconds. P1D is not PT24H across a transition. Projection
   and bounds checks use the resulting instant and normative display zone.
6. Raw floating DTSTART/RRULE stays floating even when display defaults are made
   explicit on the copy. Source VTIMEZONE blocks and raw recurrence bodies remain
   authoritative, including custom definitions overriding known names. Raw versus
   visible record contradictions still cancel export. No occurrence expansion.

## VTIMEZONE generation

Replace all BP transition/last-rule queries. Historical rows supply exact before/
after offset seconds, wall transition time and explicit post-transition DST kind.
Initial prefix comes from the model's initial type. A fixed future is represented
as fixed only when the normative tail explicitly proves it. Historical offsets
outside RFC 5545's representable +/-23:59:59 must fail export without clamping.

For unlimited future rules, evaluate normative M/J/N rules (including negative,
end-of-day and multi-day clocks) with Gregorian arithmetic and synthesize RFC
annual patterns. Verify candidates over the complete 400-year Gregorian cycle,
including neighbouring source years for year rollover, and choose the first
occurrence strictly after the final history boundary. This is a proof of the
periodic rule, not a finite export horizon. If no lossless RRULE representation
is proven, fail that definition explicitly; never append a finite RDATE future
and label it unlimited. Export the requested alias as TZID and leave existing
embedded definitions unchanged. Rule generation and point resolution must use
one immutable model.
