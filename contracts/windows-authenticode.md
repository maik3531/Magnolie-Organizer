# Windows Authenticode source boundary (#560)

The official Windows build now uses a shared signature policy and explicitly
signs only the named product-owned executable/library outputs. Existing vendor
signatures are not replaced. The payload inventory includes extensionless MZ
files and executable/MSI candidates; invalid signatures, missing timestamps and
verification failures reject the output. Product-owned files require the exact
publisher, while vendor files retain their own verified publisher.

The official NSIS branch invokes the signing hook before embedding its
uninstaller and requires successful completion. The hook clears its inherited
configuration references before the signing callback, returns a SHA-256 receipt
for the same file, and reports failures without serializing signing exceptions.
The build removes its temporary protected configuration in `finally` and restores
its previous hook environment. Extracted payload checks then require both the
application and the receipt-matched uninstaller. Signature reports participate
in the existing checksum/publication transaction. Ordinary unsigned/cross-build
paths do not acquire official signature or runtime-acceptance status.

## Repeatable source checks

The normal build includes synthetic PowerShell regressions for signature
policy (10 cases), inventory (14 cases) and hook contract (six cases). Fixtures
use only generated bytes, controlled signature/native-command/configuration
callbacks and owned temporary directories. They never use real certificates,
DPAPI, a signing tool, trust-store changes or an NSIS compiler/installer.

Separately, the already installed native NSIS compiler passed two canonical
hook/macro cases with controlled configuration/signing callbacks: successful
finalization with spaces/Unicode paths and failure propagation. No DPAPI, actual
signing or installer/uninstaller execution occurs. The generated inert fixture
was read back using the existing host extractor: extracted uninstaller bytes
match the exact finalizer input and its SHA-256 receipt, including an opaque
test-only overlay. This is compiler/byte-reconstruction evidence, not an actual
certificate, signed product uninstaller or native installed-package acceptance.

An additional 18 actual MSBuild boundary cases use inert snapshot markers,
invalid identity receipts and controlled verifier-process dependencies. They
verify rejection before embedding for unprepared official inputs, exact actual
directory binding, untrusted verifier hosts, preserved empty/space/comma argv,
secret isolation, successful verification preceding the marker, and bounded
timeout/process termination. Ordinary unsigned preparation and builds without
native inputs retain their existing target selection. Existing source-bound
native artifact descriptors are not rewritten or invalidated.

This boundary is necessary because signing a published sidecar does not sign the
immutable resource already embedded in the application. The audio setup helper
is embedded without a sidecar at all. The official-publisher source now connects
preparation, independent pre-publish verification and resource readback as
described below. The former unconditional temporary hold is now replaced by
actual independent verification immediately before the existing native snapshot
targets. Missing configuration, invalid receipts/hosts/paths/signatures or a
failed/timed-out verifier stop the build. Only successful verification permits
the existing source validators to run; no readiness flag grants that passage.
Unsigned test builds gain no new signing authority.

Cold source validation is separate from the later official publish: it scopes
out the caller's official flag, four external native input directories and four
public verification identity settings, and restores every value in `finally`.
Otherwise a cold source-archive rebuild would inherit inputs before preparation
and incorrectly reach the genuine signature gate without its prepared receipt.
Byte-exact source-orchestration fixtures exercise success and injected failure
with inert native callbacks and verify restored caller identity in both cases.
This does not weaken or bypass verification for the actual official publish.

The boundary executes only the verifier under the build's own source root,
passing all four actual MSBuild directory properties, including empty values.
Its public receipt/publisher/tool/host configuration is scoped around publish
and restored afterwards; it contains no signing credentials. The host must be
a Microsoft-signed PowerShell in a protected installed location, checked first
through protected OS PowerShell and its explicit security module, never by the
host that is still awaiting verification. A read lease prevents host replacement
during verification/start. The child has no signing certificate/password or
user-module search path. Native argv is used without a shell, with a shared
30-second deadline, process-tree termination and bounded joins.

`New-VerifiedSignedPhoneInputs` now implements the isolated preparation steps:
all original snapshots are obtained through the existing source-verification
targets before any signing callback; only copies are passed to that callback.
Only the binary checksum line is updated in the otherwise unchanged source
descriptor. The same validators must then produce a second, byte-identical
snapshot before input paths are returned. Eighteen controlled-callback cases
cover ordering, original preservation, property/path boundaries, failures and
tampering. `Build.ps1` now calls this preparation before official publication,
using its existing native command/signature callbacks. It passes only the
rechecked paths to publish and explicitly clears all unselected inherited
native input properties. The argument helper rechecks inventory, paths and
hashes, including negative original-input substitution and late-byte-change
tests. Ordinary unsigned builds retain their existing input selection.
Source/preparation paths reject MSBuild metacharacters, including commas, before
snapshot or signing callbacks. An inert native parser probe confirmed that a
comma in one `-p:` value becomes a second property despite native argv. Publisher
commas remain supported through scoped public environment/native arguments.

`Assert-PreparedPhonePayloadResources` reads managed manifest resources directly
with `PEReader`/`MetadataReader`, never loading the product assembly. It requires
the prepared binary/descriptor hashes, exact embedded bytes and the three
required sidecars; the setup helper remains embedded-only. Unknown embedded MZ
candidates, external/duplicate/missing resources, renamed inputs, stale expected
files and mismatching sidecars reject. Twenty-three inert metadata-fixture cases
exercise this identity check without loading an assembly. This is not signature
verification or a complete inventory of arbitrary Win32/nested archive formats.
The official publisher calls this readback after publish and after app signing;
it no longer re-signs native sidecars after embedding. The source audit checks
this ordering. These are source and controlled-helper checks, not an actual
official signing/publish run. Configured official inputs must also pass the
independent MSBuild verification before any snapshot target can embed them.

`Verify-PhonePayloadInputs.ps1` is called between preparation and publish and
again independently by MSBuild before embedding.
Its only configuration is a bounded, schema-checked identity receipt, expected
publisher, verification tool and all four actual input directories; it never accepts signing certificates/passwords
or invokes signing. It validates the rechecked inventory and hashes, applies
the existing native `Assert-Signature` policy to every binary as product-owned
(including the helper), then rechecks identity to reject late changes. Seventeen
controlled cases cover exact ownership, unsigned/untrusted/hash-mismatched
responses, timestamp/tool failures, late tampering, invalid receipts and actual
directory substitution/unselected inherited inputs. They
prove policy orchestration, not actual Magnolie chain/signature acceptance.
`PhonePayloadAuthenticode.Common.ps1` now additionally requires a bounded single
PKCS7 certificate table, one SHA256 Authenticode signer and PE digest, no legacy
countersignature, and exactly one SHA256 RFC3161 token. It checks CMS signature
mathematics and binds the TSTInfo SHA256 message imprint to the parent signature;
native Authenticode/tool verification remains responsible for file-digest,
publisher, time and chain trust. Fourteen inert DER/invalid-PE cases pass. Two
explicit installed Microsoft tool executables also passed read-only native
signature-status and envelope checks, without execution, signing, key access or
trust changes. Additionally, a copied Microsoft system executable passed the
actual installed SignTool verification, native trust, strict envelope and actual
MSBuild directory binding before the inert snapshot marker. This is genuine
system-file verification evidence, not Magnolie product/publisher, native source
descriptor, nested-payload or installable-package acceptance.

A receipt remains expected identity, not trust or release authority; it cannot
bypass the independently executed signature and actual-directory checks.

The JavaScript suite additionally executes the actual installer-audit dispatcher
with controlled extraction/verifier dependencies (eight cases). It checks exact
argument boundaries, verification after byte/payload checks, fail-closed verifier
errors, unchanged unsigned behavior and owned-extraction cleanup. It is not an
actual extraction or signature verification. The lightweight PowerShell text
checker handles here-strings and rejects unterminated strings/blocks; real
PowerShell parser checks remain a separate proof.

## Remaining acceptance gates

The checked source integration is not a signed-package or Microsoft Store
acceptance. Real NSIS hook execution/quoting, the exact signed embedded
uninstaller reconstructed by the extractor, complete nested PE/helper inventory,
actual Magnolie payload algorithms/certificate-chain/RFC3161 verification, installation and native
package/startup acceptance remain required. Synthetic callbacks cannot replace
these checks. Existing signing, device, VM, AV, installation and publication
pauses are unchanged; no package is released by adopting this source.
